<objective>
Introduce `vnd.fjs.return_profile` — the taxpayer-declared return profile (10-CONTEXT.md Decision 4).

**Research proved the phase's original assumption false and this document is the consequence.** A
scope guard driven by *store contents* cannot distinguish "the taxpayer has no brokerage income"
from "the brokerage document was never ingested" — the engine never sees the documents it cannot
read, so a store-driven guard stays silent in exactly the case TAX-16 exists for. The comparison has
to be against something the taxpayer *declares*.

The same document resolves a second, separate defect: `ReportLine.sources` is a non-empty tuple of
`{documentHash, boxPath, value}`, and the standard deduction (line 12e) derives from filing status
and checkboxes rather than from any document — so line 12e could not be expressed at all. With a
profile document, line 12e cites a real hash and a real box, and Phase 9's `tsc`-level guarantee is
left untouched.

Purpose: three of the five ROADMAP success criteria depend on this document existing.
Output: the dialect, its frozen kind vocabulary, its semantic checks, and its registration in
`finance_schema`'s `dialectSchemas`.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| taxpayer-supplied JSON blob -> a validated `ReturnProfile` | The widest new ingest surface this phase adds; every field crosses it untrusted |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-10-04-01 | Tampering (V5 input validation) | `declaredKinds` accepting an unrecognised string | mitigate | Membership checked against the frozen `kindVocabulary` on ingest, duplicates rejected, refusal names the offending kind and the known set; mutation 1 confirms the check is load-bearing. |

| T-10-04-05 | Information disclosure | Taxpayer PII appearing in a refusal message | mitigate | Refusals name field names, kinds and the permitted vocabulary — never a money value, a TIN, or a name. The dialect stores no name or TIN field at all. |
| T-10-04-06 | Elevation of privilege | The new dialect widening what a guest program can reach | accept | The guest vocabulary is the frozen four read commands (Phase 6); a dialect adds a schema, not a command. `finance_schema` is read-only and returns a JSON Schema. |
