<objective>
TAX-16's scope guard: `classifyScope`, which compares the taxpayer's **declared** kinds against the
engine's **modeled** set and refuses the whole return, naming every declared kind the engine does
not model.

10-CONTEXT.md Decision 2 fixes the shape: an unmodeled input makes the entire report an **error
result naming what is unmodeled**. A partial 1040 is never returned, so there is no way to mistake
one for a complete return. That is the strictest reading of criterion 4's "never a silently omitted
line", and it reuses the discriminated `{ kind: 'ok' } | { kind: 'error', … }` shape
`fjs/report/guard`'s `classifyRunOutcome` already establishes. **One rule, one place**: this module
is the only place a scope refusal is built, and Plan 10-08's Schedule D Tax Worksheet arm imports
`scopeRefusal` rather than growing a second, parallel refusal mechanism.

The failure this guards against is subtle enough to restate: "no 1099-DIV in the store" cannot
distinguish "the taxpayer had no dividends" from "the taxpayer had dividends and this engine cannot
read the form." A guard driven by store contents refuses only when the user happened to store an
unreadable document, and stays silent in exactly the case that matters. And the converse matters
too: a line that is *legitimately* zero — no interest declared, no 1099-INT stored — is `0n` with
the profile as its source, not a refusal. The entire distinction is carried by the declared kind set.

Purpose: this is the mechanism that makes TAX-05's "full line-by-line" claim truthful for an engine
that models six kinds out of fifty.
Output: `fjs/return/scope/module.f.js`.
</objective>
