Build the two foundational, dialect-independent modules every later plan in this phase composes
with: the shared document-base spread helper (DOC-00) and the Evo subject-derivation functions

`proof` exports.

    - Spreading the result into a larger object literal (`{ ...base('vnd.fjs.x'), extra: 1 }`)
      produces an object with both keys present, `dialect` first — property order matters. Later
      plans rely on `dialect` being the schema's first key so RTTI's struct validator reports it as
      the first failing field on a mismatched blob (Plan 05-02's criterion-1 proof depends on this).
    - `base` is typed so the literal string passed in is preserved as a literal type in the return
      type, never widened to plain `string`.
  </behavior>

    `/** @type {<D extends string>(dialect: D) => { readonly dialect: D }} */` followed by
    `export const base = dialect => ({ dialect })`. Verified directly: a plain
    `(dialect) => ({ dialect })` without this generic JSDoc annotation infers `dialect: string`
    (widened) on the returned object — confirmed by probing `tsc` with a deliberately wrong literal
    assignment that should fail and does not, until the generic annotation is added. Do not skip the
    generic annotation.

    This is the entire shared base today — one field. Do not add speculative fields (no `sourceRef`,
    no `createdAt` — nothing this phase's requirements call for). State in the module docstring that
    if a later dialect (Phase 11+: W-2, 1099-DIV, etc.) needs to widen this base, that is a signal
    worth noting in this docstring at that time, per DOC-00's own text, not something to pre-guess
    now.

    Document the exact spread idiom callers use: `{ ...base('vnd.fjs.1099int'), payerTin: string, ... }`,
    and that `dialect` being spread first is what lets RTTI's struct validator short-circuit to the
    discriminant on a mismatched blob.

  <behavior>
    - `artifactSubject(hash)` is the identity function on the hash string — DOC-01: "the artifact
      chain ... is rooted at the cBase32 hash of the original artifact", i.e. the subject IS that
      hash, not a derived/prefixed value. It is still exported as a named function (not used inline
      as `x => x`) so every call site reads its intent and there is a single place to change if a
      namespacing convention is ever added.
    - `formSubject({ payerTin, recipientTin, accountNumber, taxYear, formType })` is deterministic:
      called twice with two DIFFERENT plain objects carrying the SAME five field values returns two
      `===`-equal strings (proves it does not accidentally key on object identity).
    - Changing exactly one of the five fields (in isolation, holding the other four fixed) changes
      the returned subject string, for each of the five fields in turn.
    - The encoding must not be ambiguously joinable — i.e. two different five-tuples must not be
      able to collide by a field boundary shifting (e.g. `accountNumber: '1:2'` vs
      `accountNumber: '1', extra: ':2'`-shaped ambiguity). Use `JSON.stringify` on an array of the
      five values in a fixed order (`[formType, String(taxYear), payerTin, recipientTin, accountNumber]`)
      rather than manual delimiter-joining — `JSON.stringify` already escapes embedded quote/comma/
      colon characters correctly and this repo already uses this exact technique elsewhere
      (`fjs/exact/module.f.js`'s `show` helper), so no new serialization logic is invented here.
  </behavior>
  <action>
    Export `artifactSubject` and `formSubject` per the behavior above.
    `taxYear` is a plain JS `number` (a 4-digit calendar year) — this is not money, so
    `Number()`/plain numeric handling is fine here; do not route it through `fjs/types/decimal`.
    Type `formSubject`'s parameter with a local JSDoc `@typedef` naming exactly the five fields
