<!-- fjs/cas/evo/module.f.d.ts — the refresh lever. -->
```
export declare const buildCache: <O extends Operation>(cas: Cas<O>) => Effect<O, Cache>
```
`buildCache` does a full rescan of the store and returns a fresh `Cache` — the simplest of the two
available levers (the other, `syncRevision`, needs the hash+bytes handed to it directly, which an
external `cas add` invocation does not give the server); a full rescan is the right choice for this
project's realistic scale (a personal tax return's worth of documents, not a production-scale store).

<!-- fjs/protocol/mcp/module.f.d.ts — toolEntry/okResult, to build casRefreshTool as an MCP tool. -->
```
export declare const toolEntry: <T extends Type, O extends Operation>(name, description, inputRtti: T, handle: (args: Ts<T>) => Effect<O, ToolsCallResult>) => ToolEntry<O>
export declare const okResult: (text: string) => ToolsCallResult
```
An empty struct schema `{}` is a valid `inputRtti` for a zero-argument tool (this project's own
`evo_list` already uses an all-optional-fields schema for a similar "no required input" shape).

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| filesystem CAS store <-> running server's in-memory cache | Anything written into the store by ANY process with filesystem access becomes foldable into the cache by `cas_refresh` — the boundary is filesystem access, not the MCP protocol. |
| `cas_refresh` caller | Any MCP client that can reach the running server can trigger a full-store rescan. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-04-01 | Tampering | `cas_refresh` -> `buildCache` | accept | `buildCache` folds in any well-formed `vnd.fjs.revision` blob found in the store, regardless of how it got there; authorization of WHO may write to the store is already handled at the filesystem layer by Phase 2's `node --permission --allow-fs-write=<home>/.cas` scoping (SEC-01) — this plan adds no additional authorization layer, and none is in scope (deeper provenance/authorization of run-time writers is Phase 7's run-record concern, PROV-03). |
| T-05-04-02 | Denial of Service | `cas_refresh` (full rescan) | accept | A full `buildCache` rescan is O(store size); a client could call it repeatedly. Accepted for this project's realistic scale (a personal tax return's worth of documents — dozens, not millions, of stored blobs) and because the call is explicit/agent-invoked, not automatic on every read. Revisit if store size ever grows past a personal-use scale. |
| T-05-04-03 | Tampering | `cas-refresh-cross-process.test.js` (the `@ts-nocheck`, impure test file) | mitigate | Scoped to exactly one file, outside the pure `fjs/` tree, with the reason documented both in the file's leading comment and in `fjs/todo/upstream-node-spawn-effect.md` — not a silent or repo-wide relaxation of `tsconfig.json`'s strictness (no flag in `tsconfig.json` itself changes). |

</threat_model>
