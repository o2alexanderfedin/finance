From node_modules/functionalscript/fjs/types/rtti/module.f.d.ts:
```
export declare const string: String
export declare const number: Number
export declare const array: <T extends Type>(t: T) => Array<T>
export declare const record: <T extends Type>(t: T) => Record<T>
export declare const option: <T extends Type>(t: T) => Or<readonly [T, undefined]>
```
`option(T)` is what makes a struct field optional in the derived `Ts<>` type (DOC-11) — a field typed
`option(string)` becomes `fieldName?: string` in the derived type, and an object literal omitting the
key entirely type-checks. This was verified directly: `option(true)` (matching `revisionSchema`'s
`archived` field) is the correct shape for DOC-12's CORRECTED flag — present-and-`true`, or the key
entirely absent, never `false`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| vision-model output -> `vnd.fjs.ocr` | The agent's own vision pass produces `fields`/`pages` content — untrusted relative to the typed layer that will eventually be built from it. |
| any stored blob -> dialect validators | Any content addressable by hash could be handed to `validate` (a wrong dialect's blob, a corrupted/truncated blob, an adversarially-crafted blob claiming a dialect it does not match). |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-02-01 | Spoofing | `fjs/document/1099int` `validate` | mitigate | Exact-literal `dialect` discriminant checked structurally by `rttiValidate` before any other field is trusted or read — proven by Task 3's Success-Criterion-1 leaf, with a grep gate forbidding prefix-string shortcuts. |
| T-05-02-02 | Tampering | `fjs/document/1099int` `checkReferences` | mitigate | Every present money-box field is re-parsed through `fjs/exact`'s exact decimal parser; a value that does not round-trip exactly (extra precision, comma grouping, garbage) is rejected with `error(...)`, never silently coerced or truncated. |
| T-05-02-03 | Information Disclosure | `payerTin`/`recipientTin`/`accountNumber` fields | accept | These are real SSN/EIN-shaped values once real documents are ingested; this phase's scope is storage/read correctness (DOC-02's project-local, gitignored, `node --permission`-scoped store, already landed in Phase 2, is the mitigation layer) — no additional encryption-at-rest or redaction is introduced here; out of scope per the phase boundary ("this phase stores and reads; it does not calculate" and no retraction/archival story yet, DOC-15, later). |
