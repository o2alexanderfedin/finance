<objective>
Build `fjs/types/rational/module.f.js` — an exact rational number type (`[numerator, denominator]`
bigint pair), exact arithmetic (`add`, `multiply`, `sum`), and one named rounding mode: `halfUp`,
IRS half-up rounding, ties away from zero at both signs. This is the computation-layer half of the
exact-arithmetic module (EXACT-01, EXACT-03, EXACT-04); the storage/wire decimal-string layer is
Plan 02.

`fjs` genuinely has nothing usable here (verified, not assumed — see 04-CONTEXT.md): `bigfloat` is
two exports (`multiply`, `decToBin`), `prime_field` is crypto modular arithmetic, and
`divUp`/`roundUp` in `fjs/types/bigint` round up only and truncate rather than floor on negatives
(`divUp(-7n)(2n) === 0n`, not `-4n`) — disqualifying for a form full of losses, not merely
inconvenient. Nothing here reuses `divUp`/`roundUp`. Per AGENTS.md's staging rule and 04-CONTEXT.md's
locked decision, this is written as a self-contained, generic module under `fjs/types/` (mirroring
upstream `fjs/types/bigint`, `fjs/types/bigfloat`) so it can move into FunctionalScript unchanged —
this file has zero finance-specific content; "cents" and "money" framing live in Plan 02's
`fjs/exact/module.f.js`.

Purpose: rounding is a property of a 1040 line, never of a value (`round(sum(x))`, never
`sum(round(x))`) — a money type that rounds on construction must not exist, and `Math.round`'s
`-2.5 -> -2` asymmetry is a systematic bias in the taxpayer's favor on every loss that this module
exists to avoid.
Output: `fjs/types/rational/module.f.js` exporting `of`, `ofInt`, `negate`, `add`, `multiply`, `sum`,
`halfUp`, with a `proof` tree covering exact construction, exact arithmetic, rounding ties at both
signs (with the explicit Math.round divergence), and the round-vs-sum-then-round counterexample.
`npm test` and `npx tsc --noEmit` both green at the end of Task 2.
</objective>

From `node_modules/functionalscript/fjs/common/monoid/module.f.js` (+ its `.d.ts`):
- `fold: <T>({ identity, operation }: Monoid<T>) => (list: List<T>) => T` — reduces a `List<T>`
  accumulator-first (`identity op a op b op c`, left to right), seeded at `identity`. This is the
  upstream idiom `sum` composes with, not a hand-rolled `reduce`.
- `Monoid<T> = { readonly identity: T; readonly operation: Reduce<T> }` where
  `Reduce<T> = (a: T) => (b: T) => T`.

From `node_modules/functionalscript/fjs/types/list/module.f.js` (+ its `.d.ts`, type-only import):
- `List<T>` — a plain `readonly T[]` satisfies `List<T>` directly (one of `NotLazy<T>`'s variants);
  no special wrapping needed for `sum`'s array-literal test inputs.

From `node_modules/functionalscript/fjs/asserts/module.f.js`:
- `assert: (v: boolean, msg?: unknown) => asserts v` — throws `msg` if `v` is `false`; narrows `v`
  to `true`, and narrows any boolean *expression* passed as `v` (e.g. `assert(m !== null)` narrows
  `m`).
- `assertEq: <T>(a: T, b: T, msg?: unknown) => void` — `===` comparison.

House style, from `fjs/exec/module.f.js` (read for pattern only — do not import it):
- Type imports as a top-level `/** @import { Name, Name2 } from '...' */` comment per source
  module, never inline `@type {import('...').Name}`.
- `proof` co-located in the same `module.f.js` as the code it tests.
- A one-task-lifetime stub body is a bare `throw 'not implemented'` (not `todo()` — avoids an extra
