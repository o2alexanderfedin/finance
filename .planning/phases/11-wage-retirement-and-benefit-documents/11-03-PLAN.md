<objective>
Add `finance_documents_list` (MCP-08): a host-side MCP tool that enumerates stored documents as a
JSON array of `{ subject, dialect, taxYear, hash }`, active by default, `archived: true` opting in
— mirroring `evo_list`'s own convention. This is the "documented answer to 'I uploaded the wrong
document'" success criterion's read-side half (the write side is Plan 11-02's `archived` flag plus
the already-existing `evo_add` tool — no new archiving tool is added here, per CONTEXT's explicit
rejection of a `finance_document_archive` convenience wrapper).

Purpose: an agent needs to discover what is already stored — including documents whose dialect it
does not recognize, and including archived ones on request — before it can read, correct, or
retract anything.
Output: `fjs/server/finance_documents_list/module.f.js`, exporting `financeDocumentsListTool` and
its own `proof`. This plan does NOT register the tool into `financeMcpHandlers` — that is Plan
11-05, which must land in the same commit as `fjs-run-integration.test.js`'s new call (the
non-negotiable same-commit ordering constraint).
</objective>

    Create `fjs/server/finance_documents_list/module.f.js`. Define a LOCAL, deliberately loose
    schema `documentIdentitySchema = { dialect: option(string), taxYear: option(number) }` — per
    CONTEXT/RESEARCH, do NOT import or validate against `finance_schema`'s `dialectSchemas`
    registry (that would conflate "not one of our dialects" with "structurally invalid", and force
    importing every dialect just to reject unknown ones). rtti permits properties a schema does not
    mention, so any real document (which always carries `dialect: string` and `taxYear: number` per
    every existing dialect's own schema) validates against this loose schema trivially.

    Define the response entry shape (a `DocumentListEntry` JSDoc typedef):
    `{ readonly subject: string, readonly dialect: string, readonly taxYear?: number, readonly hash:
    string }` — `taxYear` genuinely optional (a malformed/no-dialect blob may carry none), assembled
    with the conditional-spread discipline (`...(taxYear === undefined ? {} : { taxYear })`), never
    a plain `{ taxYear: possiblyUndefined }` (that passes `tsc` under `exactOptionalPropertyTypes`
    and inserts a literal `taxYear: undefined` key at runtime — a real, previously-shipped defect in
    this repo).

    Missing-dialect sentinel: when a parsed snapshot's `dialect` field is absent (structurally
    possible under the loose schema), use the literal string `'unknown'` as the response's
    `dialect` value (RESEARCH.md Assumption A2 — CONTEXT does not name a sentinel; document this
    choice in the module docstring as a deliberate, arbitrary-but-recorded pick, not a discovered
    convention).

    Implement `financeDocumentsListTool = evo => cas => toolEntry('finance_documents_list',
    <description>, { archived: option(true) }, ({ archived }) => ...)`. Handler body: `step(
    evo.list(archived), subjects => foldStep(pure(subjects), /** @type {readonly
    DocumentListEntry[]} */ ([]), subject => acc => step(evo.head(subject), heads => foldStep(
    pure(heads), acc, headHash => innerAcc => mapStep(<entryFor subject headHash>, entry => entry
    === undefined ? innerAcc : [...innerAcc, entry])))))` — one row PER (subject, head) PAIR, not
    one row per subject (RESEARCH.md Open Question 2's recommended, more literal reading of
    CONTEXT's `{ subject, dialect, taxYear, hash }` shape naming a single `hash`; document in the
    module's own docstring that a subject with N concurrent heads yields N rows sharing the same
    `subject`). `evo.list(archived)` is called with the BOOLEAN `archived` (`true` or `undefined`)
    directly — NOT the string `'true'` (that string convention belongs only to `fjs_run`'s guest
    `CasOp` vocabulary, which this host-side tool never goes through).

    The per-(subject, headHash) entry builder: `step(evo.revision(headHash), revResult => ...)` —
    if `revResult[0] === 'error'`, return `pure(undefined)` (skip: should not happen for a hash
    `evo.head` itself just returned, but code defensively per `noUncheckedIndexedAccess`
    discipline). Else `cBase32ToVec(revResult[1].snapshot)`; if `null`, `pure(undefined)` (skip).
    Else `step(collectRead(cas.read(snapshotHash)), blobResult => ...)` — if
    `blobResult[0] === 'error'`, `pure(undefined)` (skip: a genuinely broken/missing blob). Else
    `utf8ToString(blobResult[1])`, then this project's own `parse` (from `fjs/json/module.f.js`,
    NEVER the host `JSON.parse` — a `.f.js` module has no `try`/`catch` and `parse` is already total,
    `Result<Unknown, string>`) — if `parse` errors, `pure(undefined)` (skip: the "non-JSON snapshot
    blob" case). Else `rttiValidate(documentIdentitySchema)(parsed)` — narrow via the `[t, v]`
    destructure pattern (never a cast, never a non-null assertion), derive `dialect` (present value
    or `'unknown'` sentinel) and `taxYear` (present value or `undefined`), and `pure({ subject,
    dialect, ...(taxYear === undefined ? {} : { taxYear }), hash: headHash })`.

    Final `.map`/`mapStep` wraps the accumulated list into `okResult(jsonText(list))` — use this
    project's own `stringify` (imported as `jsonText`, exactly as every other server module does),

    Type the exported const precisely: `@type {<O extends Operation>(evo: Evo<O>) => (cas: Cas<O>)

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Local agent (MCP client) -> `finance_documents_list` (host-side tool) | An authorized local caller enumerates the store's own content, including archived documents on request — a HOST administrative capability, not a sandboxed guest report program |
| Stored CAS content -> `finance_documents_list`'s classification logic | Any bytes ever written to the store (by this project or by `npx functionalscript cas add`) can be the input to this tool's per-document parse/classify step |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-11-03-01 | Tampering | `financeDocumentsListTool`'s per-(subject, head) entry builder | mitigate | A malformed/adversarial stored blob (non-UTF-8, non-JSON, valid JSON with a garbage `taxYear`) is handled via the loose `documentIdentitySchema` validate-then-narrow pattern and treated as a skip (non-JSON) or an `'unknown'`-tagged entry (no dialect field) — never a crash, never a cast, never a thrown exception reaching the transport. Proven by `brokenSnapshotSkippedNotCrashed` and `missingDialectFieldUsesSentinel`. |
| T-11-03-02 | Information Disclosure (accepted, by design) | `archived: true` opt-in | accept | Listing archived documents necessarily reveals their subject/dialect/hash to the caller. This is intentional and consistent with the Architectural Responsibility Map: `finance_documents_list` is a HOST-side administrative tool for an authorized local user inspecting their own store, not a sandboxed guest report program — it is NOT the boundary DOC-15's guarantee protects (that boundary is `fjs_run`'s guest vocabulary, closed in Plan 11-02). An accepted risk, not a gap. |
| T-11-03-03 | Tampering | Dialect classification | mitigate | Never derived from `finance_schema`'s `dialectSchemas` registry (would conflate "not one of ours" with "structurally invalid"); a genuinely unknown dialect tag is listed verbatim, proven by `unknownDialectListedWithRealTag`, so "I uploaded the wrong thing" never becomes silently invisible. |
</threat_model>
