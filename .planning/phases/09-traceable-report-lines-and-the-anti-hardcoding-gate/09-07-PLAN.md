<objective>
Close the coverage gaps a systematic mutation sweep found in `fjs/server/*` and `fjs/report/*`.
26 deliberate defects were introduced one at a time; **7 were not detected by any test.** Each item
below is one of those, with the exact mutation that survived.

These are missing PROOFS, not broken code — the code is correct today. But "correct today with no
test" is the state every defect in this project has started from.
</objective>

<the_headline_finding>
**E2 — the pin can be silently disconnected and nothing notices.**

In `fjsRunTool`'s handler, deleting `...pinFields` from the `executeRun(...)` call makes the program
run against **live heads instead of the pinned snapshot** — while `handleRunOutcome` still records
`pinned: true` and the pin fields, because those come from separately-computed locals rather than
from what was actually threaded through.

Verified: `npx tsc` clean, `npm test` **263 pass / 0 fail**.

An agent asking "run this against snapshot X, not whatever is live" would receive live data and a
run record asserting it was pinned. That is not merely an untested feature, it is a **provenance
lie** — precisely what PROV-03 exists to prevent.

Root cause is the familiar one: **no test in the suite calls `fjs_run` or `fjsRunTool.handle` with
`subject`+`parents` at all.** Every pin proof drives `runExecuteRunViaFixture` directly, bypassing
the shipped tool — the same shape as the Phase 9 defect, in a different feature.
</the_headline_finding>

<threat_model>
| ID | Threat | Severity | Mitigation |
|---|---|---|---|
| T-09-07-01 | The pin is computed but not applied; the record claims it was — an agent trusts live data as a fixed snapshot | **high** | End-to-end proof AND integration test driving the pin through the shipped tool against a store where the live head differs from the pin, asserting the RESULT reflects pinned data. |
| T-09-07-02 | A run record's own claimed fields (`pinned`, `args`, `inputs`) drift from reality unnoticed | high | Read each field back out of the persisted record and assert it, on both the ok and error arms. |
| T-09-07-03 | The size guard misclassifies a payload of exactly `previewBytes` or `guardBytes` | medium | Assert at the exact boundary byte counts, not values either side of them. |
| T-09-07-04 | `countNumericLiterals` mis-strips when a string contains `//` — a documented invariant with zero coverage | low | A case with a URL literal. |
</threat_model>

<task id="09-07-01">
<action>
Cover the pin path through the SHIPPED tool (E2, E1, E11).

Add a proof that drives `fjsRunTool.handle` — not `runExecuteRunViaFixture` — with `subject` and
`parents` supplied, against a store seeded so the **live head differs from the pinned revision**.
Assert the returned result reflects the PINNED data, not the live head. This is the assertion that
fails when `...pinFields` is dropped from the `executeRun` call.

If the `virtual` write/import split makes a single `fjsRunTool.handle` call unable to reach an `'ok'`
outcome (see that helper's header — this is a real, documented limitation), then the assertion
belongs in `fjs-run-integration.test.js` instead, where real Node has no such limitation. **Do not
substitute a fixture-level proof and call the gap closed** — the whole finding is that fixture-level
proofs bypass the tool. Put it wherever it can genuinely exercise the shipped path, and say which in
the SUMMARY.

Also add two smaller proofs on the same handler:
- `fjsRunTool.handle` called with `subject` only (no `parents`) persists a record with
  `pinned: false` — this is what E1's `&&` → `||` mutation broke undetected
- a successful run's persisted record has `pinned` matching whether the call actually pinned — E11
  hardcoded it to `false` and nothing noticed
</action>

<task id="09-07-03">
<action>
Cover the size guard's exact boundaries (R1, R2) and the audit's stripping order (A1).

- **R1/R2:** `sizeGuard`'s `<=` at both `previewBytes` (8192) and `guardBytes` (65536) can be changed
  to `<` undetected, because every existing test uses round values comfortably inside or outside the
  bands and none lands ON a boundary. Add proofs at EXACTLY `previewBytes` bytes and EXACTLY
  `guardBytes` bytes. Measure length the way `sizeGuard` itself measures it (`tryUtf8` +
  `bitLength/8n`), never `.length`, so the test and the code agree on what a byte is.
- **A1:** `fjs/report/audit`'s `stripStringsAndComments` strips strings before comments deliberately —
  its own header explains that a string containing `//` would otherwise be misread as a comment
  start. Reversing the order survives undetected because no test case contains such a string. Add
  one: a source with a URL literal, e.g. `const s = 'http://x.com'; const n = 5`, asserting the count
  is 1.
</action>
<read_first>
- fjs/server/response/module.f.js (`sizeGuard`, `previewBytes`, `guardBytes`, and how it measures bytes)
- fjs/report/audit/module.f.js (`stripStringsAndComments` and its header's stated ordering rationale)
</read_first>
