<objective>
Close the coverage gaps a systematic mutation sweep found in `fjs/exec`, `fjs/guest/*`, `fjs/run`
and `fjs/document/*`. 39 deliberate defects were introduced one at a time; 7 failed to typecheck and
were discarded, 24 were detected, **8 went undetected.**

**Everything in this plan is a missing test, not a broken implementation.** The code is correct
today — verified. Each item is a defect that could be introduced tomorrow with the suite staying
fully green at 263/0.

Worth recording what the sweep found STRONG, because it is the reason this list is short: the
import-specifier check, its ordering relative to the import itself, the template-literal refusal,
the frozen operation vocabulary, the step-budget outcome, `fjs/run`'s cross-field validation,
`money_field`'s safe-integer boundary and `ocr_amount`'s comma handling were all caught, several by
a dozen or more failing leaves at once. The security-relevant surface is well covered. The gaps are
in data-shaping code that ships real financial values.
</objective>

<task id="09-08-01">
<action>
**The 1099-INT conversion mapping (FO1) — the most consequential gap.**

`fjs/document/1099int/from_ocr/module.f.js`'s `boxLabels` maps six vision-emitted labels to six
schema fields. Swapping the targets of `'Box 2 Early withdrawal penalty'` and
`'Box 3 Interest on U.S. Savings Bonds and Treasury obligations'` leaves the suite green, because
**no proof anywhere exercises Box 2 or Box 3 conversion** — every existing `from_ocr` test uses only
Box 1, Box 4 and Box 8.

The current mapping is CORRECT. Do not change it. Add a proof that supplies a **distinct, non-round
value for every one of the six boxes** in one conversion, then asserts each field holds its own
value. Distinct values are the mechanism: identical or zero values would let a transposition pass.

Assert per field, not one aggregate comparison, so a single transposition names both fields involved.
</action>

- fjs/document/1099int/from_ocr/module.f.js (`boxLabels`, the conversion, and the existing proofs that use only boxes 1/4/8)
- fjs/document/1099int/module.f.js (the schema field names and `moneyBoxFields`)
</read_first>

<task id="09-08-02">
<action>
**Money boxes silently excluded from an exactness-check loop.**

Three mutations survived by removing one field name from a list the validator loops over:
- `fjs/document/1099int/module.f.js` — `'box6ForeignTaxPaid'` removed from `moneyBoxFields`
- `fjs/document/w2/module.f.js` — `'box8AllocatedTips'` removed from `moneyBoxFields`
- `fjs/document/w2/module.f.js` — `'localIncomeTax'` removed from the box15-20 exactness list

Each box is a plain `option(string)` structurally, so with it dropped from the loop a comma-grouped,
over-precision, or garbage amount passes validation and is stored uncorrected — a wrong number
reaching the caller with the validator reporting success.

Add a proof per money box named in each list: supply an invalid amount to THAT box specifically and
assert the validator refuses. Follow the existing `commaGroupedRejected`-style leaves. Drive it from
the list itself where the code structure allows, so a box added later is covered automatically
rather than depending on someone remembering — that self-enforcing shape is already established in
this project by the integration test's runtime tool-coverage check and by `fjs/tax/boundary`'s
generated threshold leaves.
</action>

<task id="09-08-03">
<action>
**Pin `formSubject`'s encoding, and the step budget's exact bound.**

**A) `fjs/document/subject/module.f.js`.** Reordering the encoded array's fields, or serializing
`taxYear` as a raw number instead of a string, both survive — the existing proofs assert only that
changing any one field changes the result, never what the encoding IS. Since the subject determines
which Evo history every extracted form belongs to, a silent encoding change forks the history of
every stored document with no error anywhere. Add a golden-value proof: for one fixed `FormKey`,
assert the exact encoded subject string. Comment it as a golden value whose change is a data
migration, not a refactor.

**B) `fjs/exec/module.f.js`.** `count < stepBudget` → `count <= stepBudget` survives: the refusal
message is derived from the same constant, so it does not move. Add a proof that counts ACTUAL
dispatches — a program chaining exactly `stepBudget` operations must complete, and one more must be
refused. The boundary, not the message.

**Not in scope, deliberately:** the sweep also found that moving `reads`' append to before the
dispatch survives. That module's own docstring already documents this as unobservable through the
current API, since a refusal discards `reads` either way. It becomes observable only if a future
phase returns partial reads alongside a refusal. Record it in the SUMMARY as accepted-with-rationale
rather than writing a proof that asserts nothing.
</action>
<read_first>
- fjs/document/subject/module.f.js (`formSubject`, its encoding, and the existing per-field proofs)
- fjs/exec/module.f.js (`interpret`, the step budget, and the refusal path)
