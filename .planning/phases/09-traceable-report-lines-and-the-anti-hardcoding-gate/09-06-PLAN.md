<objective>
User-directed refactor: make the anti-hardcoding guard **a separate thing**.

`classifyRunOutcome` currently lives inside `fjs/server/fjs_run/module.f.js`, a 1406-line module
that also does run orchestration, the MCP tool, and every proof for both. The guard is not about MCP
and not about CAS — it is a policy about run outcomes whose only dependency is the `Read` type from
`fjs/exec`. It does not belong in that file.

`fjs/report/` already holds `line` (PROV-01/02's traceability type) and `audit` (PROV-07's literal
count). Moving the guard there puts all three PROV-07 mechanisms in one place.

**The structural argument, which is the real one:** the defect this phase actually shipped was a
DUPLICATION — the rule existed twice and every proof bound to the copy that did not ship. A guard in
its own module with its own proofs makes a second copy conspicuous: you would have to import it and
then not use it. Buried mid-file among a thousand lines of orchestration, the duplicate read as
ordinary local code and nobody saw it for four plans.
</objective>

<context>
Verified before writing this plan:

- `RunOutcome` appears 41 times, all inside `fjs/server/fjs_run/module.f.js`. Nothing else in the
  repo references it, so it can move with the guard without a ripple.
- `classifyRunOutcome`'s only type dependency is `@import { Read } from '../../exec/module.f.js'`.
  No CAS, no MCP, no effects — there is no circular-import hazard.
- Only `fjs/server/module.f.js` imports from `fjs_run`, and only `fjsRunTool` /
  `placeJsModuleFixture`. Neither is affected.
- Phase 15's PROV-08 ("a second, non-tax report over the same documents") will need this same guard,
  which is a second reason it should not be a private detail of the tax path.

This is a **pure move plus new unit proofs**. Behaviour must not change: `npm test` must still report
258 pass, and the project-local proof count must RISE only by the number of new guard leaves added.
</context>

<task id="09-06-02">
<action>
Give the guard its own unit proofs — the ones that were impossible to write while it was a private
mid-file helper.

Add a `proof` export to `fjs/report/guard/module.f.js` covering the rule directly, each leaf
independently falsifiable:
- an empty `reads` array produces `kind: 'error'`
- a non-empty `reads` array produces `kind: 'ok'` carrying the value, the reads, and the
  `literalCount` it was given
- the refusal message names the literal count it was constructed with (so a wrong `literalCount`
  cannot pass unnoticed)
- the `'ok'` arm carries `literalCount` through unchanged

These are unit proofs of the rule. `fjs_run`'s existing gate proofs remain and stay green — they
cover the rule as reached through a real run, which is a different claim.
</action>
