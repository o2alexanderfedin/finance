<objective>
Close the gap Phase 9's own verification found: **the zero-read gate is implemented twice, and every
proof exercises the copy that does not ship.**

`fjs/server/fjs_run/module.f.js` carries the rule at line ~204 inside the production `executeRun`
(what `fjsRunTool`, and therefore a real MCP `fjs_run` call, actually executes) and again at line
~480 inside the test-only `runExecuteRunViaFixture`. The bodies are byte-identical. Every proof —
including `proof.antiHardcodingGate.hardcodedAdversaryFailsAndIsInvariantToInputChange`, the leaf
written specifically to defeat `() => pure({ line16: 9137 })` — calls only the test helper.

The verifier demonstrated the consequence: mutating the PRODUCTION check to `reads.length === -1`,
which still typechecks, left the full suite at **258/258 green**. Mutating the test-only copy turns
two proofs red. So the mechanism works, and it is bound to the wrong code.

This is the same defect class Phase 7 shipped — a proof that mirrors a parallel implementation
rather than the real one — and 09-CONTEXT.md warned about this exact shape in its own words: *"a gate
built for an adversary that is never actually run against it is a claim, not a proof."*
</objective>

<context>
`runExecuteRunViaFixture` exists for a real reason and is not the problem. `fjs/effects/node/virtual`
cannot compose a real `writeFile` with a real `import_` in one session — `writeFile` stores an array
of `Vec` chunks while `import_` requires a `JsModule` function. That is a structural property of the
test double, documented in Phase 7. The helper is a legitimate workaround for materialization.

The defect is narrower: the helper also **re-implements the zero-read rule** rather than sharing it.
Duplicating a rule to work around an unrelated limitation is what created the untested path.
</context>

<task id="09-05-01">
<action>
Extract the zero-read classification into a single function in `fjs/server/fjs_run/module.f.js` and
call it from both places.

Name it `classifyRunOutcome`. It takes the `literalCount` and the interpret result, and returns the
`RunOutcome` — the `'error'` arm when `reads.length === 0`, the `'ok'` arm otherwise. It is the ONLY
place in the file where `reads.length === 0` appears and the only place the zero-read error message
is constructed.

Replace the body at approximately line 204 (inside `executeRun`) and at approximately line 480
(inside `runExecuteRunViaFixture`) with calls to it. Both currently construct the identical message
`report produced zero observed reads over any stored document (source contains ${literalCount}
numeric literal(s)) — a computed report must read at least one stored document`; that string must now
be built in exactly one place.

Do not change the rule's behaviour, the message text, or the `RunOutcome` shape. This is a pure
extraction — the observable behaviour before and after must be identical, which the existing 258
passing tests are the evidence for.

Export `classifyRunOutcome` so it can be referenced by name in a proof.
</action>
