## WARNING — a real, not-blocking, coverage gap worth closing before Phase 13

Every truth above is independently, functionally verified — including two truths this
verifier confirmed by directly executing production code, not by reading a claim. The
phase goal **is achieved in the codebase today.** The following is a testing-discipline
gap, not a goal-achievement failure, but it is exactly the shape of risk AGENTS.md's own
"fourth signature defect" section warns about, so it is reported plainly rather than
smoothed over:

- **No committed, regression-tested proof exercises the full production chain
  (`form8949` → `schedule/d` → `sdtw` → `dispatchLine16` → `form1040Report`) for a
  non-degenerate §1250/28%-rate case (branch 2a) reaching an `'ok'` outcome.**
  `12.1-04-SUMMARY.md` itself says as much ("Task 2 acceptance criterion verified without
  a new committed proof leaf" — verified via an *uncommitted* one-off script). This
  verifier reproduced that exact scenario independently (Truth #2's live run,
  $7,176.00 via `scheduleDTaxWorksheet`), which is why Truth #2 is marked VERIFIED rather
  than UNCERTAIN — but nothing in `npm test` would catch a future regression that silently
  broke this specific path (e.g., a Phase 13 refactor of `form1040/core`'s dispatch call
  site).
- **The one committed proof that does check the Schedule D → dispatcher wiring
  (`cleanGainDeclaredScheduleDWiresLineSevenAAndTheFourDispatcherFields`,
  `fjs/form1040/core/module.f.js:2577-2604`) uses a fixture with no 1099-DIV forms at
  all**, so `scheduleD18Cents`/`scheduleD19Cents` are `0n` on BOTH the real code path and a
  hypothetical hardcoded-zero mutant — the assertion `outcome.scheduleD18Cents ===
  independentScheduleD.line18` would pass identically either way for this fixture. This is
  the same "proof whose expected side is not independent of a real branch value" shape
  AGENTS.md documents four prior instances of.
- **A stale comment on a currently-passing assertion.** The committed leaf
  `absentBasisRefusesTheWholeIncomeLinesCallBeforeAnyLineIsBuilt`
  (`fjs/form1040/core/module.f.js:2611-2635`) asserts `wholeReportOutcome.kind === 'error'`
  with a comment claiming this fires "via the PRE-EXISTING scope refusal... not yet via
  this task's own new absent-basis mechanism." That was true when Task 1 landed; it is no
  longer true now that Task 2's reclassification has shipped — this verifier confirmed live
  that the SAME fixture now refuses via the NEW absent-basis mechanism
  (`message` names the document and the missing box; `unmodeled: []`), not the old one. The
  assertion itself still holds (`kind === 'error'` either way), so the suite stays green,
  but the comment now misdescribes which mechanism the test is actually exercising.

**This looks like an intentional, acknowledged scope cut** (the SUMMARY names it directly
and explains why: Task 2's file list restricted `fjs/form1040/core/module.f.js` to one
line). Recommend closing it with a small follow-up plan before Phase 13 builds further on
this chain — add one committed proof through `form1040Report(...)` with a non-degenerate
§1250 or collectibles fixture, and correct the stale comment. Not treated as a phase
blocker because the underlying behavior is independently and directly confirmed working
against production code, not merely claimed.
