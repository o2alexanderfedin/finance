## Summary

The Schedule D Tax Worksheet (SDTW) is **47 printed lines**, structurally a superset of the
already-shipped 25-line QDCGT: lines 1–21 are QDCGT's lines 1–20 with two extra terms spliced
in (Schedule D lines 18/19 at SDTW lines 11, 35, 41), and lines 22–34 are QDCGT's 0%/15%/20%
tax computation reindexed. Lines 35–43 are new: the 25%-capped unrecaptured-§1250 add-on and
the 28%-capped collectibles add-on. Lines 44–47 close exactly like QDCGT's 22–25, calling back
into `baseTaxForAmount` twice. **No new arithmetic primitive is needed** — every operation is
`min`, `max`, subtract-with-floor, or a rate multiply already used by `qdcgt`.

Three findings should change what gets planned, not just how it gets built:

1. **CONTEXT.md's necessity claim for `section1202Gain` is FALSE as stated.** The dispatcher's
   guard is `scheduleD18Cents > 0n || scheduleD19Cents > 0n` — only collectibles (line 18) or
   unrecaptured §1250 (line 19) unlock branch 2a. Section 1202 gain (1099-DIV box 2c) has **no
   path to either line** unless the taxpayer separately claims a §1202 EXCLUSION on Form 8949
   (code `Q`), which requires data this dialect cannot supply (the exclusion percentage, which
   depends on when the *fund* acquired the underlying QSB stock — not on anything a 1099-DIV
   prints). Modeling `section1202Gain` for this phase should mean "stop refusing it because its
   dollar amount already flows through box 2a with no separate worksheet term," not "implement
   the §1202 exclusion machinery." See "Falsified or Unresolved Premises."
2. **Schedule D line 21 (the $3,000/$1,500 loss cap) is not in CONTEXT.md's enumerated scope
   list, but Form 1040 line 7a cannot be computed correctly without it.** Schedule D's own
   line-16 routing is a three-way branch (gain → line 16 to 7a; zero → 0 to 7a; loss → the
   *capped* loss on line 21 to 7a), confirmed against the printed form face. Any brokerage
   return that nets to a loss needs line 21, and "a brokerage sale flows all the way to line
   16" is silent about the loss direction. Recommend treating lines 17/20/21/22 as implicitly
   in scope (they are the routing/closing lines any working "Schedule D" module needs) while
   explicitly excluding the *multi-year* carryover (Schedule D lines 6/14, the Capital Loss
   Carryover Worksheet) — that is TAX-17, Phase 15, by the roadmap's own tiering.
3. **A genuinely-absent 1099-B box 1e (noncovered security) has no correct arithmetic
   answer, and CONTEXT.md does not decide what the engine does about it.** This is the
   concrete case criterion 3a's mutation gate needs to exist at all. See "Open Questions."

**Primary recommendation:** build the SDTW as a straight transcription mirroring `qdcgt`'s
shape (same rounding, same `baseTaxForAmount` reuse, same "assert don't floor" idiom on
lines that cannot go negative), add ONE new proof asserting `qdcgt(...).line25 ===
sdtw(...).line47` on a shared degenerate input (Sch D 18/19 = 0, no Form 4952) — this is the
"10-RESEARCH.md degenerate-equivalence differential" the roadmap has been deferring since
Phase 10 — and resolve the two open questions below (absent-basis handling; the exact
`filingScheduleD`/line 7a wiring) explicitly, in writing, before task-level planning, rather
than letting them surface mid-execution.

### Pattern 1: The worksheet module (mirror `qdcgt`)
**What:** One exported pure function per worksheet, a flat record keyed `line1`...`lineN`
(never an array — `noUncheckedIndexedAccess` would make every read `T | undefined`), each
`const` preceded by a comment quoting the printed instruction it implements.
**When to use:** SDTW, 28% Rate Gain Worksheet, Unrecaptured Section 1250 Gain Worksheet —
all three, per TAX-15.
**Example (verified source, this session):**
```js
// Source: i1040sd.pdf, "Schedule D Tax Worksheet," p.15-16 (2025 rev., Dec 11 2025)
// 22. Subtract line 17 from line 16. This amount is taxed at 0%.
const line22 = line16 - line17
// No printed floor on this line (unlike QDCGT's analogous line 9, this one CAN be
// legitimately smaller inputs cannot make it negative given line17 = min(line14,line16),
// so assert rather than float, matching qdcgt's documented idiom).
assert(line22 >= 0n, ['SDTW line 22 must never be negative', line22])
```

### Pattern 2: Category aggregation over documents (mirror `schedule/b`)
**What:** `sumBoxOverDocuments` / `documentLine` / `totalLine` idiom, reimplemented locally
in `fjs/form8949` (NOT imported — `fjs/form1040/core` does not export them; `fjs/schedule/b`
already established "reimplement an idiom you cannot import" as the precedent).
**When to use:** Building Schedule D lines 1b/2/3/8b/9/10 (the four A/B/D/E category totals)
from stored 1099-B documents.

### Anti-Patterns to Avoid
- **Deciding "table or worksheet" once for the whole SDTW.** Lines 44 and 46 price
  *different* amounts (line 21 and line 1) and must dispatch independently, exactly as
  QDCGT's lines 22/24 do — this is the single defect QDCGT's own docstring exists to warn
  about, and it recurs structurally in SDTW.
- **Trusting `applicableCheckboxOnForm8949` as the source of the category.** CONTEXT.md 2.4
  already forbids this; it is restated here because it is also an IRS-instructions-verified
  anti-pattern: the payer's letter is informational, never authoritative (a substitute
  statement "may also tell you which box to check" — advisory language, not "must").
- **Treating 1099-DIV box 2c (§1202 gain) as automatically driving Schedule D line 18.** It
  does not, absent an exclusion election this dialect cannot express. See Finding 1 above.
- **Hardcoding the SDTW line-19 breakpoint as a new literal.** It is already stored data —
  see "Code Examples."

**Key insight:** Every piece of arithmetic this phase needs already exists somewhere in the
repository, transcribed from a printed form. The actual work is composition and the
categorization/absent-basis decisions below — not new math.

## Common Pitfalls

### Pitfall 1: Deciding the SDTW's base method once
**What goes wrong:** An implementation computes `baseTaxForAmount` once (for line 21) and
reuses the `method`/algorithm for line 1's tax too.
**Why it happens:** It looks like redundant work to call the $100,000 seam twice.
**How to avoid:** Call `baseTaxForAmount` independently for line 44 (amount on line 21) and
line 46 (amount on line 1) — exactly as QDCGT already does for its lines 22/24. A return
whose line 21 is under $100,000 while line 1 is over it (or vice versa) is a legitimate,
reachable case (see Worked Example 2 below, where this is exactly what happens).
**Warning signs:** A test suite where `method44` and `method46` are never asserted
independently, or where no fixture pushes line 21 and line 1 to opposite sides of $100,000.

### Pitfall 2: Conflating "basis not reported to the IRS" with "basis absent"
**What goes wrong:** `box12BasisReportedToIrs` (drives A vs B / D vs E) is treated as
equivalent to `box1eCostOrOtherBasis === undefined`. They are independent: a broker can
know the basis and simply not have reported it to the IRS (box 12 unchecked, box 1e
present) — that is category B/E, fully computable. Only a **genuinely absent** box 1e
(most often paired with `box5NoncoveredSecurity`) has no basis to compute a gain from at
all. `fjs/document/1099b`'s own docstring already states this distinction as a *dialect*
concern; this phase is where it first has *computation* consequences. See "Open Questions."
**Warning signs:** Any code path that does `centsFromString(box1e ?? '0.00')` before
checking presence.

### Pitfall 3: Assuming §1202 gain (1099-DIV box 2c) needs worksheet treatment
**What goes wrong:** Building a §1202-exclusion pipeline (Form 8949 code `Q`, 28% Rate Gain
Worksheet lines 2/6) that this dialect cannot actually drive, because the exclusion
percentage depends on facts (the underlying QSB stock's acquisition date **by the fund**)
that no 1099-DIV box reports.
**Why it happens:** CONTEXT.md 1.1 lists `section1202Gain` alongside the two kinds that
really do gate branch 2a, inviting the reader to build all three the same way.
**How to avoid:** Treat box 2c as already-included, pass-through data inside box 2a
(Schedule D line 13); do not build the exclusion machinery this phase. Document the
boundary the way `fjs/document/1099div` already documents its box-8/box-7 boundary.
**Warning signs:** A plan task naming "Form 8949 code Q" or "§1202 exclusion percentage" as
this phase's scope.

### Pitfall 4: Missing lines 17/20/21/22 because CONTEXT.md's bullet list says "15, 16, 18 and 19"
**What goes wrong:** Building `fjs/schedule/d` as only the four named lines, leaving Form
1040 line 7a wired directly to Schedule D line 16 — which is wrong on every year the return
nets to a loss (see Finding 2 above; a loss must route through line 21's $3,000/$1,500 cap,
never straight from line 16).
**How to avoid:** Implement Schedule D lines 1a through 22 in full; explicitly scope OUT
only the *multi-year* carryover (lines 6, 14, and the Capital Loss Carryover Worksheet —
TAX-17, Phase 15). Document a hardcoded "no prior-year carryover" assumption at the two
lines it touches, the same way `fjs/schedule/b` documents its Form 8815 boundary.

### Pitfall 5: Reproducing the Schedule D line 20 form/instructions discrepancy incorrectly
**What goes wrong:** "Fixing" `fjs/tax/line16`'s existing stricter condition
(`filingForm4952 && form4952Line4gCents > 0n`) to match Schedule D's own printed line 20
face text ("are you filing Form 4952?" — no 4g test at all), because it looks like a bug
once this phase starts reading the real Schedule D form.
**Why it happens:** The form face and the worksheet header genuinely disagree, and a reader
seeing the form face for the first time (rather than the already-researched dispatcher code)
has no reason to prefer the stricter reading.
**How to avoid:** Do not touch it. **This research RE-VERIFIES the discrepancy against
TY2025 documents** (not merely TY2024, which is what the original Phase 10 research used):
- `f1040sd.pdf` p.2, line 20: *"Are lines 18 and 19 both zero or blank **and you are not
  filing Form 4952**?"* — no test of the amount on line 4g at all.
- `i1040sd.pdf` p.15, Schedule D Tax Worksheet header: *"Complete this worksheet only if
  line 18 or line 19 of Schedule D is more than zero and lines 15 and 16 are gains **or if
  you file Form 4952 and you have an amount on line 4g**, even if you don't need to file
  Schedule D."*
The worksheet's own header is the stricter, governing rule (it is the worksheet you would
actually be entering), and it is what `fjs/tax/line16`'s branch 2b already implements. The
discrepancy still stands, unchanged, for TY2025.

### Reusing `ordinaryBrackets` for SDTW line 19's breakpoint (verified, not hand-typed)

// Source: fjs/tax/params/module.f.js, ordinaryBrackets — already stores this exact figure
// twice (as the 24% bracket's ceiling / the 32% bracket's floor). IRC §1(h)(1)(A)(ii)
// defines the SDTW line-19 threshold by reference to "the dollar amount at which the

const twentyFivePercentThresholdCents = status => taxParamSet => {

        ['expected a 24% bracket with a ceiling for this status', status])
    return centsFromString(twentyFourPercentBracket.ceiling)
}

// marriedFilingJointly -> $394,600.00 — matches the SDTW's own printed line 19 exactly.

## Form 8949 — Category Rules (A–F), Verified

Source: `i8949.pdf` pp.3-4, "Part I"/"Part II" sections; `f1040sd.pdf` p.1, lines 1a-b/2/3/8a-b/9/10.

**TY2025 finding not anticipated by CONTEXT.md: the form now prints TWELVE boxes, A through
L, not six.** `i8949.pdf`'s own "What's New" section: *"New boxes G, H, and I for short-term
digital asset transactions... New boxes J, K, and L for long-term digital asset
transactions."* Boxes G/H/I and J/K/L are the exact digital-asset (Form 1099-DA) mirrors of
A/B/C and D/E/F respectively, added because Form 1099-DA (digital assets) is a new,
separate information return this project has no dialect for. **This does not change the
categorization logic for `vnd.fjs.1099b`-sourced transactions** — A-F remain exactly what
they always were — but a plan or proof that says "Form 8949 has six categories" is now
stating something the current printed form contradicts; say "six categories reachable from
`vnd.fjs.1099b`, of twelve the form prints" instead.

| Box | Term | Basis reported to IRS? | 1099-B received? | This phase's kind derivation |
|---|---|---|---|---|
| A | Short-term | Yes (1099-B box 12 checked) | Yes | `box2ShortTermGainOrLoss && box12BasisReportedToIrs` |
| B | Short-term | No (box 12 unchecked) | Yes | `box2ShortTermGainOrLoss && !box12BasisReportedToIrs` |
| C | Short-term | — | **No** | **OUT OF SCOPE** (deferred, per CONTEXT.md) |
| D | Long-term | Yes | Yes | `box2LongTermGainOrLoss && box12BasisReportedToIrs` |
| E | Long-term | No | Yes | `box2LongTermGainOrLoss && !box12BasisReportedToIrs` |
| F | Long-term | — | **No** | **OUT OF SCOPE** |
| G-L | (Digital assets, Form 1099-DA) | — | — | **OUT OF SCOPE** (no dialect) |

Exact verified text: *"Box A or Box G. Report on Part I with box A or box G checked all
short-term transactions reported to you on Form 1099-B or Form 1099-DA... with an amount
shown for cost or other basis **unless** the statement indicates that amount wasn't
reported to the IRS."* / *"Box B or Box H. Report ... without an amount shown for cost or
other basis or showing that cost or other basis wasn't reported to the IRS."* / *"Box C or
Box I. Report ... for which you can't check box A, B, G, or H because you didn't receive a
Form 1099-B or Form 1099-DA."*

**Undecided by any dialect field, must be handled**: a transaction where NEITHER
`box2ShortTermGainOrLoss` NOR `box2LongTermGainOrLoss` is `true` (broker didn't know the
holding period — per `i8949.pdf` p.2: *"If box 2 on Form 1099-B... is blank... your broker
doesn't know whether your gain (or loss) is short term or long term. Use your own records
to determine..."*). This project's dialect has no "use your own records" fallback field.
Recommend refusing (a computation-level refusal, distinct from the scope guard — see "Open
Questions") rather than guessing a holding period, since guessing wrong changes the tax
rate. `box2Ordinary` (the third checkbox) should also route to refusal — it signals
ordinary income (e.g., market discount), not a capital gain/loss at all, and is out of
scope by the same DOC-14/1.4-style reasoning as wash sales.

## Falsified or Unresolved Premises

### Premise checked and found FALSE: "the §1250/28%/§1202 kinds are required together"
CONTEXT.md Decision 1.1: *"The §1250/28%/§1202 kinds are required, not optional: without
them the `scheduleDTaxWorksheet` branch is unreachable and criterion 2 cannot be
satisfied."* Re-reading `fjs/tax/line16/module.f.js`'s actual branch-2a guard:
```js
if (scheduleDLinesFifteenAndSixteenAreBothGains
    && (scheduleD18Cents > 0n || scheduleD19Cents > 0n)) {
```
Only `scheduleD18Cents` (collectibles, fed by `collectibles28RateGain`) or
`scheduleD19Cents` (unrecaptured §1250, fed by `unrecaptured1250Gain`) are tested.
`section1202Gain` (1099-DIV box 2c) has **no direct path to either variable** — box 2c
flows to Schedule D line 13 (already inside box 2a's total) and only reaches the 28% Rate
Gain Worksheet (feeding line 18) if the taxpayer separately claims a §1202 EXCLUSION via
Form 8949 code `Q`, which needs the exclusion percentage (50/60/75/100%, driven by when the
underlying QSB stock was acquired **by the fund**) — data no 1099-DIV box carries.
**Practical consequence for planning:** the plan does not need to build §1202 exclusion
machinery to satisfy ROADMAP criterion 2 (making branch 2a reachable). `unrecaptured1250Gain`
OR `collectibles28RateGain` alone is sufficient and necessary; `section1202Gain` should be
reclassified as modeled by simply removing its refusal and passing box 2c's value through to
Schedule D line 13 as already-included data, with the exclusion mechanism explicitly out of
scope. This is a SMALLER task than CONTEXT.md's phrasing implies, not a blocker — but a plan
built on the "all three required" premise risks over-building §1202 machinery unnecessarily,
or under-building it if a task literally tries to make box 2c "drive" line 18 and finds it
structurally can't without more data.

### Premise unstated by CONTEXT.md, now resolved: cent-exact vs. whole-dollar (assumption A2)
CONTEXT.md 3.2 asked this research to resolve, defaulting to cent-exact if it could not.
**It can be resolved, and the default is correct for the right reason.** `i1040sd.pdf` p.9,
"Rounding Off to Whole Dollars": *"You can round off cents to whole dollars on your
Schedule D. If you do round to whole dollars, you must round all amounts."* This is the
SAME optional, taxpayer-elected rounding as Form 1040's own page-23 election
(`applyWholeDollarElection`, applied once over the whole report) — not a
worksheet-specific mandate. There is no separate rounding instruction anywhere in
`i1040sd.pdf` for the Schedule D Tax Worksheet itself (its own page carries no rounding
note distinct from Schedule D's). **Status: VERIFIED, not assumed.** Build the SDTW
cent-exact, exactly like QDCGT, and let the existing whole-dollar election apply uniformly
at the report level if/when a taxpayer elects it — do not build a second, worksheet-local
rounding rule.

## Open Questions

1. **What happens when a stored `vnd.fjs.1099b` document's box 1e (cost/basis) is
   genuinely absent?**
   - What we know: DOC-07 already models the absence distinctly from zero, and its own
     `criterion2GainConsequence` proof demonstrates the dollar consequence with a
     proof-local helper. Criterion 3a requires this consequence to be reproven against
     REAL production code once Form 8949/Schedule D compute real gains.
   - What's unclear: CONTEXT.md does not say what the ENGINE DOES when this happens in
     production — refuse the whole return, refuse just that transaction (excluding it from
     the aggregate with a citation explaining why), or `assert`-crash (an uncaught throw,
     technically "loud" per AGENTS.md's bare-throw convention, but not a graceful
     `Form1040Error`-shaped refusal a caller can render).
   - Recommendation: model it as a computation-level refusal shaped like the existing
     `Form1040Error`/`Line16Outcome` pattern (a tagged `{ kind: 'error', ... }` result Form
     8949/Schedule D can return and `form1040/core` threads through exactly as it already
     threads `line16Outcome`'s error arm) — NOT a new entry in the frozen 50-kind
     vocabulary (this is a document-data-sufficiency problem, not a declared-kind scope
     problem, and `fjs/return/scope`'s vocabulary is explicitly frozen at 50 this phase).
     A minimal `assert`-based version (crash loudly, un-gracefully) may be an acceptable
     narrower v1 if the phase owner wants to keep this phase small, but that trade-off
     should be made explicitly, not discovered mid-execution.

2. **Is `filingScheduleD` determined by the presence of `capitalGainsOrLosses` alone, or by
   any stored 1099-B?**
   - What we know: a taxpayer with ONLY capital gain distributions (1099-DIV box 2a, no
     1099-B) does not file Schedule D at all — that is dispatcher branch 2d, already
     working. `filingScheduleD` must be `true` only when actual Form 8949 transactions
     exist.
   - What's unclear: whether "actual Form 8949 transactions exist" should be read off the
     declared kind (`capitalGainsOrLosses` present in `declaredKinds`) or off the document
     store (any `vnd.fjs.1099b` present) — these could disagree (a taxpayer could hold a
     1099-B with all boxes blank, or declare the kind with no document, which the scope
     guard already prevents from reaching computation).
   - Recommendation: derive `filingScheduleD` from the declared kind (consistent with how
     `fjs/return/scope`'s docstring already reasons about "the engine never sees documents
     it cannot read" — kind declaration is the load-bearing signal throughout this
     codebase, not document presence).

3. **Does the 28% Rate Gain Worksheet / Unrecaptured §1250 Worksheet need EVERY line
   modeled, or only the reachable ones (per the recommendation in "Code Examples")?**
   - Recommendation given above: model only the lines this project's dialects can
     populate (line 4 / line 11 respectively), with every other line hardcoded to its
     zero-equivalent and the boundary documented in the module's docstring, mirroring
     `fjs/schedule/b`'s Form 8815 boundary precedent. This should be confirmed with the
     phase owner before planning, since it is a scope-narrowing decision CONTEXT.md does
     not make explicitly (it only says "TAX-11... including the Schedule D Tax Worksheet,"
     not which sub-worksheet lines).

### Mutation Gates (criterion 3a / DOC-07)
