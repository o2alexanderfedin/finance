<objective>
Close the gap this phase's own audit exposed: `fjs_run` is the product, and every proof of it
runs under `fjs/effects/node/virtual` — a mocked filesystem, mocked stdio, and no separate OS
process. Plan 07-08 is titled "end to end" but substitutes a `JsModule` stand-in for
materialization, because `virtual`'s `writeFile` (an array of `Vec` chunks) and its `import_`
(which requires a `JsModule` function) are **representationally incompatible** — verified
against upstream source. Write-then-import therefore cannot be composed in a virtual session at
all, so the product's central seam is currently evidenced only by a mock.

This plan proves that seam for real, following the precedent already established by
`cas-refresh-cross-process.test.js`, whose own header states the principle: *"an in-process
simulation does not test the thing that breaks."*
</objective>

<context>
**Why this is a root-level `.js` file with `@ts-nocheck`, not a `.f.js` proof.**
Two independent reasons, both already documented in `fjs/todo/upstream-node-spawn-effect.md` and
both already applied to `cas-refresh-cross-process.test.js`:

1. TypeScript cannot resolve `node:child_process` / `node:test` / `node:assert` / `node:fs` /
   `node:os` / `node:path` without `@types/node`, and AGENTS.md forbids adding any dependency —
   including a devDependency — without every repo owner's approval. That approval is not being
   sought to typecheck a test harness.
2. `fjs/effects/node` has no subprocess-spawn effect, so a genuinely separate-OS-process test
   cannot be written as a pure `.f.js` proof. AGENTS.md's carve-out for root-level impure JS
   (`index.js`, `all.test.js`, `cas-refresh-cross-process.test.js`) covers exactly this case.

**Do not** copy `cas-refresh-cross-process.test.js` wholesale. Read it for the spawn/handshake
plumbing — process startup, readiness detection, JSON-RPC framing, teardown — and reuse that
shape. Its subject matter (an external `cas add` racing a running server) is unrelated to this
plan.

**Keep the fast loop fast.** The 133 project-local proofs run in milliseconds; a real-process
test costs seconds. TEST-04 requires the two layers be separable, so `npm test` stays the
per-commit loop and the integration layer runs before a phase is marked complete. Conflating
them pushes developers to skip both.
</context>

| T-07-09-03 | The test pollutes the developer's real CAS home or the repo working tree | medium | A fresh `mkdtemp` home per run, removed in teardown. Assert the repo tree is unchanged after the run. |

| T-07-09-05 | Diagnostics leak into stdout and corrupt the JSON-RPC stream (MCP-05's invariant, previously only asserted under `virtual`) | high | Assert every stdout line parses as JSON-RPC across the whole real session — the first time this invariant is checked against a real process. |
</threat_model>

<task id="07-09-01">
<action>
Create `fjs-run-integration.test.js` at the repo root: a real-process JSON-RPC integration test
for `fjs_run`.

Structure it with the same plumbing shape as `cas-refresh-cross-process.test.js` — `@ts-nocheck`
header stating both reasons, `node:test` + `node:assert/strict`, `spawn` from
`node:child_process`, `mkdtemp` under `os.tmpdir()` for an isolated CAS home, and a `finally`
teardown that kills the child and removes the temp home.

The session must drive a genuinely separate `node index.js <home>` process over real stdin/stdout
through, in order: `initialize`, `notifications/initialized`, `tools/list`, then `tools/call`.
Detect readiness by matching the `initialize` response's JSON-RPC `id` — never by a timer.

Seed the CAS home before the run with several `vnd.fjs.1099int` documents whose
`box1InterestIncome` values differ, **including one where the field is absent**, and store a
program that sums the field across every stored 1099-INT. Reuse the same seeding approach Plan
07-08's proof uses so the two agree on document shape; the difference here is that the store is a
real directory, not a virtual root.

Assert: the returned total equals the independently-computed expected sum with the absent-field
document contributing nothing; `resultHash` and `runHash` are both present and both resolve to
real content in the store; and the materialized program `.mjs` exists on the real filesystem in
the gitignored materialization subdirectory Plan 07-05 established.
</action>
