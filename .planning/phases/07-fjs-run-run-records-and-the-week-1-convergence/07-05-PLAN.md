<objective>
Build the two genuinely new mechanisms Success Criterion 1 depends on and that no existing code
in this repo performs (07-RESEARCH.md's Critical Finding, Pitfall 1, Pitfall 3): (1) actually
writing a stored program's bytes to a real file at its hash-derived materialization path, in a
dedicated gitignored subdirectory, and (2) a synchronous host map for `interpret`'s
`OperationMap<CasOp, string>` built by resolving the whole reachable CAS/Evo store into plain
data BEFORE `interpret` ever runs — the same snapshot the pinning decision (subject/parents
resolve once, at call time) also requires.

Purpose: `fjs/guest/materialize/module.f.js`'s `loadProgram` (Phase 6) assumes the file at its
target path already exists; nothing in this repo has ever written it. And `interpret`'s
`OperationMap` requires plain synchronous handlers, never `Effect`-returning ones, so the real
`casRead`/`evoList`/`evoHead`/`evoRevision` implementations cannot be thin wrappers around
`Cas`/`Evo`'s effect-returning methods.
Output: `materializeProgram` (new export in the existing materialize module) and
`buildRunSnapshot`/`buildHostMap` (a new module), both independently proof-tested, ready for
Plan 06 to compose into the `fjs_run` handler.

**Documented scope note on proof technique** (read before implementing Task 1's proof): under
`fjs/effects/node/virtual`, `writeFile` stores a file as an array of `Vec` chunks, while
`import_` requires the entry at its path to be a `JsModule` (a plain function) — verified by
reading `node_modules/functionalscript/fjs/effects/node/virtual/module.f.js`'s `writeFile`/
`import_`/`readFile` implementations directly. `virtual` has no JS parser and cannot execute
freshly-written bytes as a module, so writing real bytes and then importing them cannot be
composed in the SAME virtual session — this is a structural property of the test double, not a
gap in this plan's design. Task 1's proof therefore verifies the write mechanism on its own
terms (write, then read the same bytes back via `readFile`/`readUtf8File` at the same path,
asserting equality) rather than chaining into an `import_` call. Phase 6's own
`underVirtual.cleanProgramImportsAndRuns` proof (unchanged, already proven) remains the
evidence that import-from-a-materialized-path works, using its established `JsModule` stand-in
for "materialization already succeeded." Plan 06/08's end-to-end proofs compose the two
established techniques side by side (assert the write happened correctly; separately, seed a
`JsModule` at the same conceptual path to exercise execution) rather than pretending `virtual`
can do both in one call — production code still performs both steps for real, since real
Node's `import()` reads whatever `writeFile` actually wrote to disk.
</objective>

      — `blobs` maps every cBase32 hash `cas.list()` returns to its decoded UTF-8 text (via
      `collectRead`/`utf8ToString` or the fjs `fromVec`/`tryUtf8` pairing already used
      elsewhere in this repo); `heads` maps every subject (active and archived, from
      `evo.list()`/`evo.list(true)`) to its current head hashes (from `evo.head(subject)`);
      `revisions` maps every hash that `evo.revision(hash)` successfully decodes (skip, don't
      error, for hashes that are not valid revisions — mirrors `buildCache`'s own
      "ignore non-revision blobs" precedent) to `JSON.stringify(RevisionData)`.
    - `buildRunSnapshot = cas => evoApi => pin => Effect<..., RunSnapshot>` where
      `pin: { subject: string, parents: readonly string[] } | undefined`. When `pin` is
      supplied, `heads[pin.subject]` in the resulting snapshot is OVERRIDDEN to `pin.parents`
      — regardless of what the live store's current head for that subject is — so a caller can
      re-run against a fixed revision even if the store has since moved on. Every other
      subject's heads resolve live, as normal. This function resolves the WHOLE store
      (`cas.list()`'s full result, every subject `evo.list()`/`evo.list(true)` returns) in one
      pass, per 07-RESEARCH.md's Open Question 2 recommendation (simplest-correct at this
      project's scale; revisit only if this becomes a real performance problem).
    - `buildHostMap = (snapshot: RunSnapshot) => OperationMap<CasOp, string>` returns an object
      with exactly four keys (`casRead`, `evoList`, `evoHead`, `evoRevision`), each a plain
      synchronous `(a: string) => string` closure reading ONLY from `snapshot` (never
      performing I/O, never returning an `Effect`): `casRead` looks up `snapshot.blobs[hash]`
      (throw a plain string, e.g. `` `blob not found: ${hash}` ``, if absent — `interpret`'s own
      `assert(typeof thrown === 'string')` catch-and-report path already handles a thrown
      string correctly, so this is consistent with the project's bare-throw discipline, never
      an `Error`); `evoList` returns `JSON.stringify` of `snapshot.activeSubjects` or
      `snapshot.archivedSubjects` depending on its string argument; `evoHead` returns
      `JSON.stringify(snapshot.heads[subject] ?? [])`; `evoRevision` returns
      `snapshot.revisions[hash]` (or throws a not-found string).
  </behavior>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| CAS/Evo store -> host map snapshot | The snapshot is resolved once, server-side, before any guest code runs; the guest never sees a live effect-returning store handle |
| written program file -> real filesystem | The materialize directory is content-hash-named and gitignored, never committed |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-07-05-01 | Tampering | materialized program file location | mitigate | Dedicated subdirectory (`.fjs-run`), gitignored, hash-derived filename — a materialized file can never collide with or overwrite `.cas`'s own sharded store or an unrelated repo file |
| T-07-05-02 | Elevation of Privilege | host map handler shape | mitigate | Every handler is structurally a plain `(a:string)=>string` function, so it cannot perform I/O even if a future edit tried — `tsc` rejects an `Effect`-returning handler against `OperationMap<CasOp,string>` |
| T-07-05-03 | Repudiation | snapshot pin override | mitigate | Pinning only ever overrides the ONE named subject's head entry in the snapshot; every other subject still resolves its live head, so pinning cannot be used to silently rewrite unrelated provenance |
</threat_model>
